# Generated x64 code-size experiment — 5 September 2026

## Result and scope

This experiment reduces actual machine code in both compiler implementations.
It does not compress executables, introduce a loader, remove language features,
or change the external ABI. Old and new compiler revisions intentionally emit
different bytes; matching current Python/self-hosted paths still agree.

All sizes are bytes. Machine code means the unpadded PE `.text` virtual size
or the executable ELF `PT_LOAD` segment's file size. Section/page padding
explains why file savings do not exactly match instruction-byte savings.

The baseline is the released 1.2.4 compiler (SHA-256
`DE7FAF4095146D466A8D7F0C17422D3EF0375647385DB36470792FDF72960F18`),
used to rebuild the same current sources, not a comparison against stale
application binaries. Baseline MiniDoc and benchmark builds explicitly use
`--no-object-pipeline`; the compiler control uses the canonical object path.
The optimized compiler image includes the fixes described below in both
the control and candidate program sources.

The initial benchmark, before adding the optional `--long` argument, shrank
from 1,559,040 to 1,536,512 bytes on Windows and from 1,712,432 to 1,687,856
bytes on Linux. Its shorter runtime measurements are retained separately.

## Changes retained

- Use AL/EAX/RAX accumulator-immediate opcodes where they are shorter; retain
  sign-extended imm8 where that remains the shortest form.
- Encode a shift count whose actual imm8 byte is one with the implicit-one
  instruction. Zero and other counts retain their previous flag behavior.
- Narrow `AND r64, nonnegative-signed32-mask` to its zero-extending 32-bit form.
  The result and defined flags remain identical; negative/sign-extended masks
  are never narrowed.
- Fold `Jcc yes; JMP no; yes:` into `J!cc no; yes:` only for an adjacent,
  unlabelled tail. Earlier labels and relative relocations keep their offsets.
- Refresh the ML Linux syscall/pthread blob, labels and external fixups
  together. Its canonical length falls from 1,998 to 1,989 bytes.

### Additional pre-existing bug fixed

The object path released non-inline function bodies before emitting later
callers. Variadic escape analysis could then inspect an empty body and
incorrectly place an escaping argument array on the caller's stack.
`FunctionDef` now explicitly retains the cached escape proof after body
release; the emission clone copies that field. Function bodies can still be
freed promptly.

`variadic_escape_lifetime.ml` forces the callee into an earlier object batch,
returns from its creating caller, overwrites another call frame, invokes GC,
and reads a globally retained string/nested-array/integer tail. The released
1.2.4 MLO build reproduces the runtime failure; current Windows and Linux
monolithic/MLO images match, and the runtime regression passes.

## Runtime measurement method

Host: AMD Ryzen 9 9900X (12 cores / 24 logical CPUs), approximately 64 GB RAM,
Windows 11 Pro 10.0.26200; Linux is WSL2 kernel
`6.6.87.2-microsoft-standard-WSL2`. This is a shared desktop, not a dedicated
benchmark host. No compiler builds or test suites ran alongside the timed
comparisons; unrelated desktop activity was not terminated.

`benchmarks/compare_code_size.py` warms each image once, then executes seven
fresh-process A/B pairs with alternating AB/BA order. Every run must return
zero; the benchmark verifies equal workload checksums. All samples, including
outliers, are retained. WSL wall times include process startup; internal
millisecond counters measure individual workloads. Windows ticks are coarse,
so `--long` increases arithmetic/call iterations from 24 million to 240 million
without increasing the allocation, iterator or thread workloads.

### Runtime results

Negative paired changes mean less time. The paired column is the median of
`(candidate_i / baseline_i - 1) * 100`, not the ratio of the two independent
medians.

| Workload | Baseline median | Candidate median | Median paired change |
| --- | ---: | ---: | ---: |
| Windows, initial short run | 1.191 s | 1.183 s | -0.21% |
| Linux/WSL, initial short run | 1.496 s | 1.492 s | -0.66% |
| Windows, long arithmetic | 9.526 s | 8.443 s | -1.18% |
| Linux/WSL, long arithmetic | 8.922 s | 8.836 s | -0.38% |

The long Windows samples range from 8.389–13.130 seconds before and
8.332–10.796 seconds after. Their outliers make the apparent 11.4% reduction
in independent medians unsuitable as a compiler speedup claim. Long Linux
samples are tighter: 8.809–9.074 seconds before and 8.671–8.964 seconds after.

Not every subtest gets faster. For the long Linux arithmetic/call workloads,
median paired changes are -0.80% typed arithmetic, +1.37% dynamic arithmetic,
+2.67% auto-inlined calls and -1.27% typed out-of-line calls. Initial short
Linux medians suggested a 3–4% arithmetic/call slowdown, which did not repeat
as a broad slowdown in the longer run. The practical conclusion is **smaller
code with comparable overall measured throughput**, not a universal speed
gain or proof that no individual program can regress. Size and instruction
layout can affect hot paths differently.

All workload self-checks pass. The reported eager-iterator heap delta stays
45,620,000 bytes before and after; this is not a peak process-memory measure.
A small MiniDoc analysis smoke comparison also completed, but its roughly
67 ms duration is too short to support a meaningful application speed claim.
Full compiler API generation was a correctness/documentation check, not an
A/B application benchmark.

### Reproduction

Keep a known-good old compiler in a separate path; never overwrite it with
the candidate. From the workspace containing both compiler repositories:

```powershell
# Build identical program sources with each compiler.
& $oldCompiler MiniLangCompilerML/benchmarks/language_optimizer.ml MiniLangCompilerML/build/size_before.exe --no-object-pipeline -I MiniLangCompilerML
python MiniLangCompilerPy/mlc_win64.py MiniLangCompilerML/benchmarks/language_optimizer.ml MiniLangCompilerML/build/size_after.exe -I MiniLangCompilerML
python MiniLangCompilerPy/benchmarks/compare_code_size.py --baseline MiniLangCompilerML/build/size_before.exe --candidate MiniLangCompilerML/build/size_after.exe --runs 7 --output MiniLangCompilerML/build/size_windows.json -- --long
```

For Linux, add `--target linux-x64` to both build commands, choose distinct
output paths and add `--wsl` to the comparison command. The same source,
include-root order, heap options and target must be used within each pair.

Run `python scripts/check_linux_runtime_blob.py` from either compiler repo
with its sibling repository present. `--patch` prints a source-update patch
for review; it does not silently rewrite the embedded runtime.

## Limits and next candidates

The reduction is real but modest. This run does not establish MiniQuake or
MiniSQL throughput, compiler build-speed gains, or a reduced managed-heap peak.
Those require their own before/after workloads. General forward-branch
relaxation and selective outlining of repeated cold error/type-check paths
remain potential larger size levers, but were not implemented here. They need
separate relocation, performance and cross-compiler identity testing.
